01 · Executive summary

结论先行：先解冲突，再做视觉

原文的技术探针、状态覆盖和验收思路值得保留；以下五项是开始设计前必须统一的产品决定。

新增设计建议
Decision 01 · 阻塞冲突

实时忙态与同步 HTTP 互相矛盾

如果网络请求在 Blender 主线程同步执行，计时器、进度刷新和停止按钮可能都无法及时响应。只画一个转圈图标不能解决问题。

P0 必须决策 推荐网络 I/O 移到工作线程，Blender 数据读写仍只在主线程进行；若暂不调整架构，则界面必须明确提示“等待响应中”，不得承诺实时进度。

Decision 02 · 信任冲突

“可撤销”不能仅靠数量差证明

objects 从 3 变成 4 只能说明数量变化，不能证明材质、变换、节点图或网格修改都可以完整恢复。

P0 必须决策 回执展示“变更摘要”和“恢复能力”两个独立字段。只有经过验证的撤销/回滚路径，才显示可撤销动作。

Decision 03 · 数据语义

Token 用量与上下文预算必须分开

API 返回的 prompt/completion token 和 cache hit 是单次请求统计；上下文预算是历史消息可能占用模型窗口的估算值，两者不是同一指标。

P0 规范 主界面仅显示简明状态；本次用量与上下文预算分开记录、分开解释。

Decision 04 · 原型边界

28 个状态不是 28 套独立界面

把每个异常都画成完整新面板会导致重复、信息跳动和实现成本上升。

结构优化 收敛为 8 个状态族 + 一份状态转移表，复用固定布局，仅替换状态文案、动作和详情区。

Decision 05 · 设计边界

文档视觉与 Blender 真实 UI 要分开

这份 HTML 可以用颜色、卡片和表格帮助其他 AI 理解需求；这些视觉装饰不等于可以在 Blender Panel 内原样实现。

硬约束 插件 UI 只能用原文列出的原生控件与可写属性；所有视觉稿必须附控件映射。

Decision 06 · 安全边界

任意 Python 执行必须作为高风险动作

原型目前包含 execute_blender_code 工具。不能把“模型写代码”作为普通工具行悄悄执行，也不能用“允许执行”代替风险说明。

安全要求 默认受控工具优先；任意代码运行要显示代码/影响范围并取得明确批准，失败信息作为不可信内容渲染。

02 · Source audit

对原始文档的详细审查

“原文事实”表示来自上传文件；“设计建议”是本次审查新增，不应误认为已经在运行环境验证。

审查项原文现状 / 依据问题与风险改进决定
原文事实
控件能力		原文列出多行 UILayout.textbox、progress、template_list + UIList、图片预览、子面板、popup、Text datablock、视口自绘等，并标注哪些已测、哪些未测。技术清单散在“能力契约”和每项需求内；接手的 AI 可能只记住展示效果，忽略验证状态。合并为“已验证 / 禁用 / 需 GUI 实测”能力表，并要求每个未验证点附测试方法和 fallback。
原文事实
主线程阻塞		原文明确记录 HTTP 同步阻塞主线程，停止只能在轮次之间生效。这与实时计时、持续进度、点击即响应的忙态体验冲突；假按钮会降低信任。作为开发架构门槛处理，不是单纯 UI 美化问题。推荐队列 + 计时器桥接；暂不改架构时降级文案。
原文事实
一键撤销		原文要求用执行前后快照统计差异，并在全局撤销关闭时阻断发送。场景计数差异不等于完整 diff；全局 Undo 开启也不能自动证明任意 Python 数据写入可被整轮回退。拆成“变更回执”“Blender Undo 可用”“任务级恢复点可用”三项状态。未验证时不显示“已可撤销”。
原文事实
多轮历史		原文指出现状每条指令都是全新对话；计划使用 CollectionProperty + UIList 或折行 label；20 条历史需要三种方案。消息很长时的换行/行高/滚动未被验证；把全文塞进单行 UIList 会不可读。默认推荐“紧凑可滚动列表 + 选中消息详情”；先 GUI 验证，失败则改分页，不强依赖长行折行。
原文事实
错误态		原文覆盖缺 Key、401、402、代理 502、超时、部分完成、工具异常和截图不可用。错误文案已丰富，但动作可误导；例如超时后无法仅凭客户端状态保证服务端没有处理请求或计费。统一错误模型：发生了什么 / 场景是否变化 / 下一步推荐动作 / 是否安全重试。超时不承诺“不会重复扣费”。
原文事实
Token 展示		原文提供一条真实 usage：prompt 1576、cache hit 1408、cache miss 168、completion 61。静态原型中的比例条是示意值；单次 usage 不代表整个对话的上下文预算。把“当前请求用量”放在任务结果详情；把“上下文占用估算”放在独立状态条，标注估算/实测来源。
设计建议
按钮语义		原文有多个“停止、重试、允许执行代码、回滚”等按钮。部分动作范围不清，可能出现重复提交、重复执行工具或误触高风险操作。按钮文案必须写明对象和范围，例如“停止后续轮次”“重试本轮请求”“撤销本次任务”，避免泛化的“停止/恢复”。
设计建议
对话安全		原型 HTML 用静态字符串构建模拟内容；实际模型文本和工具结果是动态数据。未来若直接把用户/模型文本拼进 HTML 或富文本，可能形成注入或破坏 UI。实现时对动态内容使用 Blender label/Text block 的纯文本路径；网页原型不要对非可信内容直接使用 innerHTML。
需要更正的一条原型文案：“请求超时，重试不会重复扣费”不是安全承诺。客户端没有拿到响应，并不能单凭这一点证明服务端没有处理请求或计费。新版建议文案为：“本轮请求超时，尚未收到可确认的结果；请检查执行记录。重试可能会产生新的请求费用。”如果后端实现了幂等请求 ID，再根据真实能力改写。
03 · Baseline & constraints

必须继承的事实与实现边界

以下基线整理自上传 HTML。若实际代码已变化，先重新探测和验证，再更新此表，不要把旧文档当永远有效的 API 真相。

项目基线（来自原文）

  • 目标环境：Blender 5.2.1 LTS；内嵌 CPython 3.13.13。
  • 当前模型：deepseek-flash，模型名在偏好设置中可改；原文指出 deepseek-v4-flash 已弃用。
  • 当前 5 个工具：get_scene_info、create_primitive、set_material、transform_object、execute_blender_code。
  • 原文真实样例约 4 轮 / 3.9 秒；usage 输入 1576，缓存命中 1408，输出 61。
  • API Key 目前可存偏好设置（原文注明明文）或通过 DEEPSEEK_API_KEY 环境变量提供。

硬约束（来自原文）

  • 不引入登录、账号或云同步设计。
  • 对话必须留在 Blender 内，不转外部客户端。
  • 不新增需要 pip 安装的第三方依赖；优先 Blender 内置 Python 标准库。
  • 不要假设 Blender 面板可自定义 RGB、字体、字号、圆角、阴影、渐变、透明度或 CSS 动画。
  • 只用原文白名单中的图标；未列出的图标必须现场验证，不猜名称。
  • 不要假设 Panel 有 scrollable；长面板滚动行为要 GUI 实测。
  • 后台模式无 GL 的截图能力必须降级，不可假装截图成功。
命名建议：产品 UI 顶部建议使用“Blender AI Agent”，把 “DeepSeek / deepseek-flash” 放到 Provider/模型状态位置。这样既忠实反映当前接入，也避免未来切换模型时整个产品名称和控件命名一起重做。当前版本仍按 DeepSeek 接口实现；多 Provider 是后续架构扩展，不是本次 UI 的隐性范围扩张。

信息层级（从上到下）

  1. 连接状态：Key 是否可用、来自偏好设置还是环境变量；缺失时提供直接入口。
  2. 输入与主动作：多行输入为主，执行/停止动作固定在输入区之后。
  3. 当前任务状态：请求阶段、轮次、耗时、工具执行、部分完成或最终失败。
  4. 变更回执：提交后立即出现，放在最新回复之前；一眼看出改了什么、能否恢复。
  5. 对话历史：紧凑列表 + 选中项详情，不强制使用气泡。
  6. 工具追踪、Token、截图细节：作为子面板或弹层；关键错误不能只藏在折叠区域。

为什么这样排序

  • 用户进入面板首先要知道能不能执行、输入什么、如何触发。
  • 执行过程中，状态与“停止后续执行”比历史消息更重要。
  • 任务完成后，变更回执必须在一眼可见的位置；不应让用户去翻工具 JSON。
  • 把完整 JSON、Token 细项、截图元数据放在次级入口，但错误原因与下一步不能隐藏。

真实 Blender 控件映射

  • 输入：原文实测的 UILayout.textbox(data, prop, initial_visible_lines=3, placeholder=…)。
  • 进度：UILayout.progress(type='RING'|'BAR', factor=0..1)；不能靠网页 CSS 动画假装数据在更新。
  • 历史：template_list + UIList + CollectionProperty；行高和滚动需验证。
  • 分组：原生 Panel / 子 Panel；长详情用 Text datablock，不把长 JSON 压成单行 label。
注意：上面的面板图是信息结构线框，不是 Blender 实际皮肤。设计 AI 交付时必须逐项写出原生控件 API、状态变化、实际 operator 和验收步骤；不得把 HTML 里的颜色、圆角或卡片边框照搬到 Blender 插件。
05 · Interaction contract

核心交互规则

同一个 UI 元素在不同状态下应有明确且一致的含义，不允许因为状态变化而悄悄改变按钮动作。

输入与提交

  • 默认显示 3 行多行输入；placeholder 示例要体现复合任务，而非只写“输入指令”。
  • 明确 Enter 与 Shift+Enter 的语义，并以 Blender GUI 实测结果为准。建议保留可见“执行任务”按钮，不依赖键盘行为猜测。
  • 执行开始后固定当前任务文本；避免网络等待期间用户修改输入，导致不清楚执行的是哪个版本。
  • 新提交要防重复触发；请求进行中再次点击不得创建第二个并行任务。
  • “清空输入”只清输入框，不得清空历史或删除场景对象。

停止 / 取消

  • 在模型 HTTP 请求中：按钮名称用“停止后续执行”，说明“当前请求返回后生效”。
  • 工具执行阶段：如当前工具不可中断，显示“当前步骤完成后停止后续步骤”。
  • 可中断状态必须由真实后端标记确认；不能只改按钮文案或停止 Spinner。
  • 停止后立即做任务结算：列出已完成操作、未执行步骤、是否产生场景变化以及是否提供恢复入口。
  • 如果采用同步阻塞主线程方案，UI 本身可能无法在请求期间响应，所以不得宣称点击能立即停止。

变更回执 / 恢复

  • 回执在工具执行提交后尽快显示，目标是提交后 1 秒内能看见摘要；若验证仍在进行，显示“变更已应用，正在验证”。
  • 回执最少包含：任务状态、变更对象/数据块摘要、失败/跳过项、恢复能力和详情入口。
  • 区分“Blender 全局 Undo 可用”“本次操作可通过 Ctrl+Z 恢复”“存在任务级回滚点”。这三者不能相互替代。
  • 任何不能证明可恢复的路径必须显示“未建立任务级回滚点”或“无法保证整轮恢复”，不能显示“可撤销”。

工具追踪 / 长内容

  • 每个工具行显示稳定的序号、工具名、可读动作名、状态、耗时和简短结果。
  • 状态图标只能从原文白名单选：进行中 TIME，成功 CHECKMARK，失败 ERROR，信息 INFO。
  • 点行打开详情时显示参数摘要、返回摘要和错误信息；完整 JSON / traceback 放 Text datablock，可复制。
  • 成功后也保留失败后修复的记录；明确标注“首次失败，已修复”，不要伪装成全程成功。

历史与上下文

  • 新会话、压缩历史、清空记录要区分：它们对场景没有隐式影响。
  • 压缩前给出前后条数、摘要内容、估算节省 Token；原始记录保留策略要明确。
  • 当前上下文百分比如果没有可靠估算，不展示伪精确数字；可以先显示“历史消息 20 条 / 历史预算尚未估算”。
  • 每条 AI 回复与任务 ID 关联，以便把消息、工具记录、变更回执和回滚点串起来。

颜色之外的状态可读性

  • 所有状态必须由“文字标签 + 图标 + 动作差异”表达，不得只靠红/橙/绿。
  • 示例：[失败 · 需要修改设置] + PREFERENCES 图标 + “打开偏好设置”。
  • 可重试错误使用 [请求失败 · 可重试] + “重试本轮”；不可重试错误使用 [配置错误] + “修改 Key”。
  • 状态颜色在 Blender 原生面板里不能按网页设计任意设定；本规范页面使用的颜色仅用于文档分类。
06 · State & execution

状态机和执行流程

UI 只呈现可观测状态；所有转移都要由运行时事件驱动，不能依赖“等两秒就显示成功”的演示逻辑。

READY输入可编辑 / 显示 Key 与模型状态
→
PREFLIGHT校验 Key、撤销/恢复能力、重复任务
→
REQUESTING等待模型响应 / 计时 / 可请求停止后续
→
TOOL_RUNNING逐步显示工具名、轮次、返回摘要
→
VERIFYING检查工具结果与场景差异
→
COMPLETED生成回执 / 记录日志 / 可恢复性说明

失败或停止分支：任一阶段 → PARTIAL / FAILED / STOPPED → 结算实际已发生的场景变更 → 显示安全的下一步。工具返回错误可回喂模型继续修复，但必须保留首次错误。

推荐的最小非阻塞实现

  1. 工作线程只处理网络 I/O 和响应解析；不得访问或修改 bpy 数据。
  2. 工作线程通过线程安全队列投递状态、文本和 Tool Call 数据。
  3. bpy.app.timers.register 在主线程轮询队列，更新 UI 并执行 Blender 数据操作。
  4. 所有 Blender API / RNA / operator 操作都在主线程执行；每个工具动作有开始、成功、失败和耗时事件。
  5. HTTP 请求设置真实超时；停止按钮设置 cooperative stop 标记，在当前请求结束后阻止后续轮次。

若暂时不调整同步架构

  • 不要显示“每秒实时变化”的假计时或进度条。
  • 只在请求开始前显示“正在发送请求；当前 Blender 界面可能暂时无响应”。
  • 停止按钮在无响应期间不可用，必须把这一限制写清楚；不能把“停止后续轮次”描述成立即取消请求。
  • 将“主线程非阻塞”列为下一版明确技术债和验收项，而不是把问题推给 UI 设计。

强烈建议 产品体验要求和同步实现只能二选一，不能同时宣称全部实现。

07 · State inventory

把原来的 28 个状态合并为 8 个状态族

不是删除原有边界条件，而是让状态共享同一套布局与交互规范。原始编号保留在括号中，方便开发对照。

01 配置与连接 关键

原状态 1–5、16–17：缺 Key、Key 来源、401、402、代理失败、单轮超时。复用连接区 + 专用错误说明 + 唯一下一步动作。

02 空闲与输入

09 · Conversation history

20 条历史：三种实现方案与推荐

原文要求必须比较三种方案。推荐先做最稳的主方案，并保留无滚动依赖的 fallback。

方案 A · 推荐

紧凑 UIList + 详情区

列表每条只显示角色/状态/单行摘要/时间或序号；用户选择一条后，在列表下显示该条完整正文。长内容不塞进行高不确定的列表行。

  • 优点：20 条可浏览、单条可读、能标出失败工具。
  • 前置：GUI 实测 template_list 的滚动条、行高、键盘选择行为。
  • 失败 fallback：切换方案 B。

实测后采用

方案 B · 稳定 fallback

分页历史，每页 4–5 条

只渲染当前页，以“上一页 / 下一页 / 第 N 页，共 M 页”浏览；每条摘要点选后显示详情。

  • 优点：不依赖滚动；窄面板布局更可控。
  • 缺点：翻页成本较高，新消息追加时需要处理页码。
  • 适用：UIList 行高、滚动或刷新行为不可靠。

不依赖滚动

方案 C · 辅助归档

Text datablock 完整转录

对话记录镜像到 bpy.data.texts，通过 template_ID(space, "text") 选择、打开和复制完整文本。主面板仍保留最近消息与摘要。

  • 优点：完整记录易复制、适合长 JSON / traceback。
  • 缺点：不是理想的日常聊天浏览体验。
  • 适用：导出、调试、完整审计记录。

不作为主聊天 UI

推荐决策：方案 A 为主、方案 B 为 GUI 验证失败后的退路、方案 C 负责复制与归档。不要在第一版同时实现三套主 UI，也不要把“UIList 一定可滚动/自动跟底”当成未经测试的事实。
10 · Error copy system

错误文案模板与下一步动作

每类错误要告诉用户：发生什么、场景是否已变化、下一步优先做什么。动作必须能真实实现。

01 · 未配置 API Key 配置阻断

未配置 DeepSeek API Key。请打开“编辑 → 偏好设置 → 插件 → Blender AI Agent”填写，或设置环境变量 DEEPSEEK_API_KEY。
主动作：打开偏好设置（PREFERENCES）。次级说明：Key 来源与保存风险；输入框本身不回显 Key。

02 · API Key 无效（401） 不可盲重试

DeepSeek 返回 401：API Key 无效。请检查当前 Key 是否正确、是否被撤销，然后再重试。
主动作：修改 Key；不要把“重试”作为首选。错误原文可在详情区查看。

03 · 余额不足（402） 需外部处理

DeepSeek 返回 402：账户余额不足，当前请求未能正常完成。请先查看服务商账单或充值状态。
主动作：打开官方计费页面（只有 URL 已配置且真实有效时才显示按钮）；充值后由用户主动重试。

04 · 网络 / 代理错误（502） 可诊断

无法连接 DeepSeek：HTTP 502。检测到当前配置使用系统代理 127.0.0.1:7890；请确认代理进程正在运行，或检查网络配置。
主动作：显示代理检查步骤。只有真正执行过连通性测试才能显示“检查成功/失败”；否则按钮应叫“查看检查方法”。

05 · 单轮请求超时 状态待确认

第 2 轮请求超时（20 秒），尚未收到可确认的响应。当前轮是否已被服务端处理无法仅凭客户端超时确定；请检查工具记录后再决定是否重试。
主动作：重试本轮请求；同时提示可能产生新的请求费用。不要承诺“不会重复扣费”，除非实现并验证幂等机制。

06 · 轮次 / 时间预算耗尽 部分完成

已达到本次任务的轮次或时间预算。场景可能已发生部分修改。请先检查下面的已执行步骤和变更回执，再选择继续或恢复。
主动作：优先展示已发生变更；仅当有可验证断点时才显示“从断点继续”。恢复动作也必须说明范围。

07 · Blender 工具 / Python 异常

工具执行失败：ZeroDivisionError: division by zero。AI 已收到错误摘要；本次任务是否部分成功，以工具记录和变更回执为准。
主动作：如果 Agent 可安全修复，显示“让 AI 尝试修复”；原始 traceback 必须保留。任意 Python 运行需审批和风险提示。

08 · 请求使用了当前不存在的工具

当前版本没有可直接调用的“布尔切割”专用工具。可以查看现有工具能力，或在明确批准后使用受控的代码执行路径。
主动作：先解释可用替代方法；不要把工具不存在伪装成 Blender 本身失败。

09 · Blender 全局撤销关闭 提交前置检查

当前 Blender 全局撤销未启用。为避免操作后无法通过常规 Undo 恢复，已暂时禁用执行。请启用全局撤销，或先建立经过验证的项目检查点。
主动作：打开相关设置或显示明确步骤；启用后重新检查状态。不要仅根据用户点击就假定设置已成功变更。

10 · 视口截图不可用

本次无法获取有效视口图像（当前运行环境没有可用的 OpenGL 上下文）。已降级为场景文字摘要；视觉检查未执行。
主动作：继续使用文字检查，或提示切换到有 GUI 的 Blender 环境。绝不可将黑图当成成功截图发送。

12 · Safety & trust

安全和恢复必须成为 UI 合同

本节是实施要求，不要求本次 UI 突然增加账户体系或云功能。

API Key

  • 输入内容在 UI 上打码，但必须明确告诉用户：打码只影响显示，不代表磁盘存储加密。
  • 默认优先读取 DEEPSEEK_API_KEY；若使用偏好设置中的 Key，要显示来源。
  • 日志、错误、复制的任务书与转录中不得打印完整 Key；只可显示“已配置 / 未配置”和必要的短指纹。
  • “去偏好设置”动作必须使用真实可用的 Blender operator；失败时给出手动路径。

执行任意 Python

  • 默认将 execute_blender_code 视为高风险工具。
  • 显示代码预览、目标对象/数据范围、预计副作用和“执行一次”批准动作。
  • 禁止模型通过工具参数绕过审批；审批必须由可信 UI/运行时检查。
  • 原始返回、stdout 和 traceback 可折叠查看，但摘要、失败原因和影响范围必须可见。
  • 动态文本不得被当成可信 HTML；模型输出只用于显示，不可成为 UI 代码。

回执与恢复承诺

  • 每个 mutation tool 都要有操作前后可比较的变更摘要。
  • 区分“工具执行成功”和“结果验证成功”；不可用同一个绿色/成功状态替代。
  • 任务级回滚需要独立设计和测试；如果只是靠全局 Ctrl+Z，就准确叫“尝试使用 Blender Undo”。
  • 回滚需记录任务 ID、目标还原点、被移除/恢复的数据摘要和回滚后验证结果。

资源和日志

  • 对话/工具记录按会话和任务组织；原文可考虑本地 JSON 和 bpy.data.texts 存档。
  • 设置历史上限（原文参考 200 条 / 1 MiB）；达到上限时给出清理或归档提示。
  • 日志记录状态事件、工具名、耗时与错误类型，不记录 API Key。
  • 复制转录时可选择“含工具详情”或“仅对话摘要”，避免把冗长 JSON 全部塞进剪贴板。

18 · Open questions

开始开发前仍需要确认的决定

这些不是阻塞设计交付的问题，但实现团队必须在代码中做出明确选择。

是否愿意为真正实时的忙态重构网络请求？

推荐愿意。若坚持同步请求，UI 设计不能兑现实时计时、即时停止和持续工具状态，用户会继续感到插件卡死。最小安全做法是网络线程与 Blender 主线程分离，所有 bpy 调用仍留在主线程。

整轮 Undo 的第一版采用什么实现？

建议先让实际写操作经过可验证的 Blender Undo 操作入口，并通过真实 GUI 测试确认回退范围。任务级快照/回滚可以后续做；在没有可靠任务级机制前，UI 不能给出超出真实能力的保证。

主面板里默认要显示多少条历史？

建议默认显示可读的最近 4–5 条摘要，完整记录由 UIList 或分页浏览；新消息只在用户位于列表底部时才自动定位到最新消息。由于原文明确表示滚动和行高未验证，最终要由 GUI 实测定案。

Provider 是否马上抽象成多模型？

本轮 UI 不需要增加 MiniMax/OpenAI 等新 Provider 的功能范围，但建议避免把 DeepSeek 硬编码进产品名称。当前只保留 DeepSeek 配置和展示；Provider 抽象属于后端架构决策。
